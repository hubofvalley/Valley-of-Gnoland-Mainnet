# Mainnet v1.8.0 coordinated-upgrade readiness

> Status checked 2026-11-18, **before the mainnet halt**. This is an operator
> compatibility notice, **not** an automated upgrade procedure or approval to
> restart a validator. Recheck the official tracker and completed upgrade ledger
> before acting; a published release does not mean the upgrade has completed.

## Verified upstream transition

- Network: `gnoland-1`; coordinated halt **after block 1,651,500**, set by
  [GovDAO proposal #19](https://gno.land/r/gov/dao:19).
- Estimated halt: **2026-11-18 13:16 UTC (20:16 WIB)**, not an exact deadline.
  Block height and executed governance are authoritative, not this estimate.
- Required release **after** the halt: [`v1.8.0`](https://github.com/gnolang/gno/releases/tag/v1.8.0),
  source commit `fc79041f4cd1a7b3ed4b316dc5ac14162eb78730`.
  Its version floor prevents starting the new binary before the halt and the
  old binary after it.
- [Onyx `v1.8.0-rc.1`](https://github.com/gnolang/gno/releases/tag/v1.8.0-rc.1)
  completed its rehearsal. As of this check, the
  [mainnet upgrade tracker](https://github.com/gnolang/gno/issues/6503)
  still says **in progress** and the
  [completed mainnet ledger](https://github.com/gnolang/gno/blob/chain/mainnet/misc/deployments/mainnet.gno.land/UPGRADES.md)
  ends at `v1.7.1`.

## Grand Valley compatibility gap

At Grand Valley Mainnet `main` commit `f561c4d0af15d808204161969eba6eb1f299cc9d`,
the `1a` installer, `1b` updater, Node Doctor and supplied `gnokey` still
pin **`v1.7.0`**. Option `1b` can report "Already up to date" relative to
that **repository pin**, not relative to the live chain. It does not perform
a `v1.8.0` coordinated upgrade or multi-version replay.

[Grand Valley PR #33](https://github.com/hubofvalley/Valley-of-Gnoland-Mainnet/pull/33)
proposes `v1.7.1` rolling-release alignment, **not** `v1.8.0` support.
Do not assume either the current menu or PR #33 covers this halt. A
separately reviewed, checksum-verified, halt-aware change and an operator
recovery rehearsal are needed before Grand Valley can claim such support.

## Read-only preparation checklist

1. Check the [official upgrade tracker](https://github.com/gnolang/gno/issues/6503),
   [release notes](https://github.com/gnolang/gno/releases/tag/v1.8.0), and
   [deployment ledger](https://github.com/gnolang/gno/blob/chain/mainnet/misc/deployments/mainnet.gno.land/UPGRADES.md).
   Confirm the planned height, runtime version and actual deployment state.
2. Identify **every transaction-signing client**, including operator-console
   `gnokey`, automation, bots and external SDKs. Go clients built before
   `v1.7.1` may emit non-canonical transaction bytes. From the coordinated
   halt, `v1.8.0` refuses those transactions with `tx decode error`.
   Use signing clients built from `v1.7.1` or newer; the official notes also
   identify `amino-ts >= 0.2.1` and the ts-proto clients as canonical.
   Do **not** test this by broadcasting a transaction.
3. Verify intended node binaries and artifacts against the official release
   `CHECKSUMS.txt`, and review the existing service, backup and single-signer
   recovery plan. Never treat a staged checksum as proof of live-node safety.
4. Review the effective `halt_height` setting: upstream requires it to remain
   `0` for the normal coordinated halt. Do not bypass upgrade gates or change
   configuration merely to satisfy a diagnostic.
5. For **new nodes replaying from genesis**, `v1.8.0` alone cannot replay
   historical non-canonical transactions. Upstream requires `v1.7.1` through
   height `1,651,500`, then `v1.8.0`. A single-version `v1.8.0`
   genesis replay fails with `wrong Block.Header.AppHash`. This repository
   has no verified automatic replay supervisor for that transition.

## Boundaries and follow-up

This notice makes **no** changes to a node, signing key, transaction, source
pin, service, or upgrade configuration. Do not run the Grand Valley `1a` or
`1b` operations expecting them to install `v1.8.0`. The upstream release
also adds opt-in RPC/query configuration fields; do not infer they are enabled
or required by Grand Valley.

The implementation follow-up belongs in a separate, reviewable upgrade PR:
verify upstream tag/commit and all binary digests, preserve existing genesis
and rollback protections, handle the coordinated halt, provide a signer-client
compatibility gate and offline fixtures, and document the required manual
replay sequence. Any live-node rehearsal, cutover or recovery remains an
operator-controlled action outside this repository change.
